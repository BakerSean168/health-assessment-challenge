# AI 使用复盘

## 我如何使用 AI

本项目中，AI 主要作为**分析、实现和测试加速器**使用，而不是需求、架构或测试正确性的最终裁决者。需求边界先由挑战说明和实际产品行为确定，AI 再参与方案设计、代码实现和测试生成；最终是否接受，仍以领域规则、可执行测试和人工代码审查为准。

| 使用场景 | AI 具体参与内容 | 最终如何校验 |
|---|---|---|
| 数据库建模 | 协助拆分 `AnonymousSession`、`Assessment`、`AssessmentResult`、`Subscription`、`PaymentEvent`，讨论 1:1 / 1:N 关系、事务边界、唯一约束和 Prisma migration 方案 | 对照挑战要求审查模型是否过度设计；用真实 PostgreSQL 集成测试和数据库约束验证，而不是只相信 ORM 类型 |
| Mock / 测试数据 | 生成确定性的评估 fixture、支付测试数据以及固定 FREE / ACTIVE 评审 session；两条评审 session 使用相同答案与结果快照，仅订阅状态不同 | 计算逻辑统一走 `demo-v1` 领域函数并注入固定参考日期；生产环境通过两条 cURL 实际验证 FREE 脱敏与 ACTIVE 完整结果 |
| 复杂逻辑 | 协助实现步骤顺序策略、乐观并发控制、原子提交、支付幂等、结果快照、服务端 FREE / ACTIVE 投影以及“提交成功但响应丢失”后的恢复逻辑 | 先冻结领域规则和 API 契约，再通过单元测试、真实 PostgreSQL 集成测试和 Playwright 浏览器流程验证；AI 提议不能直接替代领域规则 |
| 测试用例 / 边界场景 | 快速枚举并生成缺失输入、非法范围、乱序步骤、过期 revision、并发写入、重复提交、支付重放、`text/plain` 写请求、持久化脏数据等测试场景 | 每个测试本身也需要人工审查；测试失败并不自动意味着生产代码错误，必须先确认测试是否真的表达了已冻结的业务规则 |

项目采用的协作流程是：

```text
需求 / 实际行为
  -> 人工确认验收条件
  -> AI 协助生成方案、测试或实现
  -> RED / 可复现失败
  -> GREEN 实现
  -> lint / typecheck / tests / build
  -> 人工审查测试与代码
```

AI 最有价值的地方不是“一次生成整个项目”，而是把已经明确的问题快速展开成候选方案、边界场景和可执行验证，再由开发者决定哪些应该进入最终实现。

## 一次我明确否决 AI 的测试

最典型的一次发生在 **T07 步骤顺序策略**。

当时需要验证：用户不能跳过尚未完成的前置步骤，但**已经填写过的步骤允许回头编辑**。AI 生成了一个名为“跳过 `HEIGHT` 应被拒绝”的单元测试，但测试直接复用了完整评估 fixture，而这个 fixture 里其实已经存在：

```ts
heightCm: 175
```

因此，对当前领域规则来说，这个请求并不是“跳过 HEIGHT”，而是在**编辑一个已经填写过的 HEIGHT**。生产代码返回 `allowed: true` 才是正确行为；如果为了让这个测试变绿而修改生产逻辑，反而会破坏“允许编辑已回答步骤”的既定规则。

我最终**否决了这个测试的原始断言，而不是修改正确的生产代码**。测试 fixture 被改成真正未完成前置步骤的状态，例如：

```ts
{
  ...completeLoseAssessment,
  goal: null,
  activityLevel: null,
  heightCm: null,
}
```

此时再尝试写入 `HEIGHT`，才真正构成跳过前置步骤，应该返回 `STEP_OUT_OF_ORDER`。

这个案例对我最重要的提醒是：**AI 生成的测试同样只是候选代码，不是“可执行的真理”**。TDD 可以约束 AI，但前提是开发者仍要审查测试是否准确表达需求；否则一个错误测试也可能把正确代码“修坏”。对应证据可见 `src/modules/assessment/domain/step-policy.test.ts`，完整开发记录保留在 `docs/07-ai-usage-log.md` 的 T07 条目中。

## 补充

补充一个发生在开始实施前的否决：
AI 在大致浏览目标文档和简单了解参考网站后就给出了一个表单方案。 但是这显然是在没有充分理解业务需求下生成的方案。
我**否决实施该方案，而是去尝试搜集相关的业务流程信息**。 最终是找到了 betterme 的全 flow 流程，充分了解其业务和状态变化后，再次生成了详细的方案。

## 最终验证证据

交付时，AI 辅助产生的代码和测试仍需通过独立验证：

- 83 个 Vitest 单元/组件测试；
- 49 个真实 PostgreSQL 集成测试；
- 2 个 Playwright 浏览器流程，覆盖 FREE 与付费完整旅程；
- GitHub Actions 中的 lint、类型检查、测试、生产构建和不可变容器发布；
- 相同的 Playwright 流程通过公共 HTTPS 生产环境验证；
- 固定 FREE / ACTIVE 评审 session 可直接通过 cURL 验证服务端差异化结果投影。
